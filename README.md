# Telegram-бот учёта инспекций

Версия 2 системы для регистрации инспекций экспертами и специалистами, автоматической сверки поставщиков, ролевого доступа и Excel-выгрузок.

## Возможности

- регистрация по общему секретному коду с подтверждением администратором;
- роли «эксперт», «специалист» и «администратор»;
- отдельные пошаговые сценарии для эксперта и специалиста;
- до 10 заказов в одной машине или смене с отдельным поставщиком для каждого номера;
- версионная загрузка общего `.xlsx` с колонками «Заказ» и «Поставщик»;
- автоматическое определение поставщика и неизменяемый снимок результата сверки;
- гибкий ввод даты (`ДД.ММ`, `ДД,ММ` или полная дата), строгая проверка номера заказа и денежных значений;
- раздельная проверка дублей для экспертной и специалистской работы;
- редактирование и восстанавливаемое удаление сотрудником собственных записей за любые месяцы, администратором — любых записей;
- подробная история изменений заказов, поставщиков, проекта, статуса, автомобиля, ставки и комментария;
- смена роли пользователя и назначение новых администраторов из меню;
- устойчивые внутренние коды проектов и сценариев;
- личная и общая статистика;
- личная Excel-выгрузка для сотрудников и полная/инкрементальная административная выгрузка на отдельных вкладках «Специалисты» и «Эксперты»;
- сохранение незавершённого диалога в Redis и данных в PostgreSQL.

Исторические справочники поставщиков остаются в БД только для совместимости и отката, но больше не доступны в рабочем интерфейсе.

## Требования

- Docker Engine с Docker Compose — для сервера;
- либо Python 3.13 и `uv` — для локальной разработки;
- Telegram-бот, созданный через [@BotFather](https://t.me/BotFather);
- Telegram ID хотя бы одного администратора.

## Настройка

### Создание Telegram-бота

1. Откройте [@BotFather](https://t.me/BotFather) и отправьте `/newbot`.
2. Укажите отображаемое имя и уникальное имя, заканчивающееся на `bot`.
3. Сохраните выданный токен в `BOT_TOKEN`. Не пересылайте его и не добавляйте в Git.
4. Через `/setdescription` и `/setuserpic` при необходимости добавьте описание и аватар.
5. Через `/setcommands` можно заранее установить команды:

```text
start - Главное меню и регистрация
add - Добавить инспекцию
my - Моя статистика
report - Общий отчёт
export - Выгрузить Excel
admin - Администрирование
cancel - Отменить текущий диалог
help - Помощь
```

Приложение также устанавливает этот список автоматически при запуске.

1. Скопируйте `.env.example` в `.env`.
2. Укажите `BOT_TOKEN` из BotFather.
3. Укажите Telegram ID администраторов через запятую в `ADMIN_TELEGRAM_IDS`.
4. Задайте общий код регистрации в `REGISTRATION_INVITE_CODE`.
5. Замените `POSTGRES_PASSWORD` и ту же часть пароля в `DATABASE_URL`.
6. Не добавляйте `.env` в Git.

Пример:

```dotenv
BOT_TOKEN=123456789:telegram_token
ADMIN_TELEGRAM_IDS=111111111,222222222
REGISTRATION_INVITE_CODE=long_random_shared_code
DATABASE_URL=postgresql+asyncpg://inspections:strong_password@db:5432/inspections
REDIS_URL=redis://redis:6379/0
APP_TIMEZONE=Europe/Moscow
POSTGRES_DB=inspections
POSTGRES_USER=inspections
POSTGRES_PASSWORD=strong_password
```

## Запуск через Docker

```bash
docker compose up --build -d
docker compose ps
docker compose logs -f bot
```

Контейнер `migrate` применяет Alembic-миграции после готовности PostgreSQL. Бот запускается только после успешной миграции и healthcheck PostgreSQL/Redis.

Остановка без удаления данных:

```bash
docker compose down
```

Не выполняйте `docker compose down -v`, если не хотите удалить базу и состояния диалогов.

## Локальная разработка

Для локального запуска нужны доступные PostgreSQL и Redis. После настройки их адресов в `.env`:

```bash
uv sync --dev
uv run alembic upgrade head
uv run python -m app.main
```

Проверки:

```bash
uv run ruff check .
uv run pytest
```

Без внешних сервисов PostgreSQL- и Redis-тесты будут отмечены как `skipped`. Для полного интеграционного прогона поднимите тестовые зависимости на локальных портах:

```bash
ENV_FILE=.env docker compose \
  -f compose.yaml -f compose.test.yaml \
  -p inspections-integration \
  up -d db redis

TEST_DATABASE_URL=postgresql+asyncpg://inspections:strong_password@localhost:55432/inspections \
TEST_REDIS_URL=redis://localhost:56379/15 \
uv run pytest tests/test_postgres_integration.py tests/test_redis_fsm_integration.py

ENV_FILE=.env docker compose \
  -f compose.yaml -f compose.test.yaml \
  -p inspections-integration \
  down -v
```

`TEST_DATABASE_URL` должен указывать только на отдельную тестовую БД: миграционный тест очищает её до и после проверки.

## Первый вход

При старте приложения записи из `ADMIN_TELEGRAM_IDS` автоматически создаются или восстанавливаются как активные администраторы. Администратор открывает бота командой `/start`.

Новый пользователь:

1. отправляет `/start`;
2. вводит общий секретный код, полученный у администратора;
3. указывает ФИО;
4. выбирает запрашиваемую роль;
5. ждёт решения администратора.

Знать Telegram ID сотрудников заранее не требуется. Секретный код отсекает посторонних, а окончательный доступ всё равно выдаётся администратором по заявке с Telegram ID. Для смены кода обновите `REGISTRATION_INVITE_CODE` и пересоздайте контейнер бота.

Администратор получает сообщение с кнопками назначения роли. В профиле активного пользователя роль можно изменить между экспертом и специалистом или назначить его администратором. Самостоятельно получить административные права нельзя.

## Команды

| Команда | Эксперт | Специалист | Администратор |
|---|:---:|:---:|:---:|
| `/add` | ✓ | ✓ | ✓ |
| `/my` | ✓ | ✓ | ✓ |
| `/report` | — | ✓ | ✓ |
| `/export` | только свои | только свои | все сотрудники: полная и новые |
| `/admin` | — | — | ✓ |
| `/cancel`, `/help` | ✓ | ✓ | ✓ |

Эксперт и специалист выгружают только собственные инспекции и не могут выбрать другого сотрудника. Такая личная выгрузка не меняет статус обработки. Администратор может выгружать всех либо выбранного сотрудника; успешная административная выгрузка фиксирует включённые строки как обработанные.

После изменения ранее выгруженной записи она снова появляется в режиме «только невыгруженные». В Excel заполняется дата внесения изменений. Колонка ГСМ удалена.

Каждый номер заказа выгружается отдельной строкой. Для дополнительного номера ставка записывается числом `0,00`, статусом становится `-`, а номер группы, сотрудник, дата, проект и служебные даты повторяются. Статус обработки также заполняется на каждой строке группы. Одна машина или смена при этом считается одной выполненной единицей.

## Файл сверки

Администратор открывает `/admin` → «Загрузить данные для сверки» и отправляет один `.xlsx` с двумя колонками:

| Заказ | Поставщик |
|---|---|
| `23000Y8798782` | `Гаффаров Камран Нахиб оглы ИП` |

Перед активацией файл проверяется полностью. Повторяющиеся номера с одинаковым поставщиком объединяются, конфликтующие поставщики отклоняют весь файл. Ошибочная загрузка не заменяет действующую версию. Если файл отсутствует или номер не найден, бот сообщает об этом и не разрешает продолжить ввод заказа.

Если создание или отправка файла завершились ошибкой, состав пакета остаётся в БД. Команда `/export` показывает последние неудачные пакеты и позволяет сформировать их повторно с тем же набором инспекций.

Даты в Excel записываются готовыми строками `ДД.ММ.ГГГГ` и `ДД.ММ.ГГГГ ЧЧ:ММ`, чтобы браузерные просмотрщики не показывали внутренние серийные числа Excel вроде `46217`.

## Smoke-test перед рабочим запуском

Создайте отдельного тестового бота, затем:

```bash
cp .env.smoke.example .env.smoke
# заполните .env.smoke тестовым токеном и Telegram ID
./scripts/smoke.sh .env.smoke
```

Скрипт использует отдельное имя Compose-проекта, создаёт чистые временные тома, применяет миграции, проверяет PostgreSQL, Redis и запуск бота, после чего удаляет только свои тестовые контейнеры и тома.

После smoke-test вручную проверьте три роли:

1. эксперт — выбор проекта до номера заказа, все проектные ветки, дубль, смена, одна машина и номер автомобиля для Х5;
2. специалист — обычная запись, одна машина от 2 до 10 заказов, автоматический проект при дубле и личный Excel;
3. администратор — загрузка/замена файла сверки, редактирование чужой записи, новые/полные выгрузки и повтор неудачного пакета.

## Резервное копирование

Сделайте скрипты исполняемыми один раз:

```bash
chmod +x scripts/backup.sh scripts/restore.sh scripts/smoke.sh
```

Создать сжатый `pg_dump` и удалить копии старше семи дней:

```bash
./scripts/backup.sh
```

Для ежедневного запуска добавьте в cron пользователя сервера:

```cron
0 2 * * * /absolute/path/to/project/scripts/backup.sh >> /absolute/path/to/project/backups/backup.log 2>&1
```

Восстановление заменяет содержимое текущей базы данными из копии:

```bash
./scripts/restore.sh backups/inspections_YYYYMMDD_HHMMSS.sql.gz
```

Перед первым рабочим запуском обязательно выполните тестовое восстановление на отдельной базе.

## Обновление

Перед обновлением рабочего сервера обязательно создайте и проверьте резервные копии текущего приложения и PostgreSQL. Не применяйте миграцию без проверенного дампа.

```bash
git pull
docker compose build bot migrate
docker compose up -d
docker compose logs -f migrate bot
```

Справочники заполняются идемпотентно: повторный старт не создаёт дубли. Деактивированные администратором элементы не удаляются из исторических инспекций.
